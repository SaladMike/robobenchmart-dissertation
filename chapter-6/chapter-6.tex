\section{Conclusions}

I set out to take two released RoboBenchMart checkpoints, run them through the benchmark's atomic protocol using only what is public, and report what happened. Three things happened. The protocol ran. The results came out far below the published ones. And the most likely reason is not the policies themselves but the distance between the checkpoints and the environment they are now evaluated in.

Running it was possible, though not as simple as the documentation implies. All 42 configurations finished for both Octo and $\pi_{0.5}$, 2,520 episodes in total, once I had restored an import that an upstream commit had removed from the floor environment, made the client read instructions through gymnasium wrappers, and given each Octo connection its own policy state. Each episode left a success flag linked to its seed, its log line and its video, with every file hashed. No per-step trajectories were saved; the evaluation script never asks for them, which is easy to miss because the empty trajectory files are still written.

The outcomes are lopsided. Pick-and-place produced nothing, 0 of 900 episodes for each model. Door closing is the only place the two checkpoints part company: $\pi_{0.5}$ closed a door in 37 of 180 episodes and opened one in 2, while Octo closed a door 4 times and never opened one. Within $\pi_{0.5}$'s closing results, Seeds, Pose and Layout (15, 10 and 12 of 60) cannot be separated at this sample size, and Pairing showed nothing because every task it applies to was already at zero.

Set against the upstream paper, these numbers are not slightly off. They are in a different place. Upstream reports 82--89\% for $\pi_{0.5}$ on Basket with training seeds; I saw 0 of 90, which no amount of sampling luck explains. Since the checkpoints were published in November 2025, upstream has changed the robot's initial joint configuration, the lighting, the robot class and the motion planner, and has regenerated the demonstrations and scenes; the scene release I evaluated on dates from January 2026. I take that version drift to be the leading explanation. I have not tested it. Some properties of the protocol limit interpretation whatever the version: door Layout reuses training scenes, every episode starts close to its fixture, actions run in open-loop chunks with success read only at chunk boundaries, and a single moved product anywhere in the store fails an episode.

Put bluntly, the released checkpoints do not reproduce the published results on the current benchmark, and the records available do not say exactly why. A leaderboard would have been a more satisfying thing to end with. For anyone planning to use these checkpoints as baselines, I suspect this is more useful.

\section{Limitations}

Thirty episodes per configuration is the most obvious constraint. It was enough to show that pick-and-place rates are low and that $\pi_{0.5}$ closes doors far more often than it opens them. It was not enough to resolve differences between conditions of the size the protocol was built to detect.

Each protocol ran once, and the two models ran differently: Octo partly serial and partly on four servers, $\pi_{0.5}$ through one shared server. Their episodes are seed-matched rather than strictly paired, and nothing here measures how much a second run would differ from the first.

Because the evidence stops at outcomes, I cannot say where failed episodes went wrong. There are no per-step trajectories, and nobody has watched the videos systematically. I have avoided guessing at failure causes, and the upstream failure taxonomy remains unused.

A few facts about the setup rest on reading the code rather than on observation at run time. The locked action indices map to the head joints by my reading of the controller order. The $\pi_{0.5}$ chunk length comes from an OpenPI default I did not check on the revision used. The GPU and several library versions went unrecorded.

The scope, finally, is narrow by design: two checkpoints, atomic tasks, simulation. Nothing here bears on $\pi_0$ or SmolVLA, on composite tasks, or on physical robots.

\section{Future work}
\label{sec:future}

If I could run one more experiment, it would be a \textbf{version-aligned re-evaluation}. Check out the upstream code as it stood in early November 2025, pair it with the scene release that preceded the January regeneration (\texttt{demo\_envs} at \texttt{2fd1681a}), and evaluate both checkpoints on two to four configurations where upstream and current results disagree most, for instance $\pi_{0.5}$ Basket and Board under Seeds. Thirty episodes each would do. Rates that climb towards the upstream figures would strongly support the drift hypothesis, and the individual changes could then be reintroduced one at a time, starting with the initial joint configuration. Rates that stay at zero would point instead at the interface between checkpoint and environment, beginning with the order of the action dimensions and the normalisation statistics.

Once some configuration has a success rate worth measuring, the cost of open-loop execution can be measured directly. An \textbf{execution-horizon sweep}, running only the first $H \in \{1, 5, 10, 25, 50\}$ actions of each chunk before querying the policy again, needs no retraining at all. Checking the success predicate after every step rather than once per chunk would separate a second, smaller effect.

None of this will explain failures unless the runs keep \textbf{better records}. Passing \texttt{--save-traj} for a subset of configurations would make per-step states available. Together with the existing videos, they would allow the upstream taxonomy to be applied under a written coding manual, ideally by more than one annotator, so that failure stages could be reported instead of guessed. Printing the controller's joint list and the policy's action horizon at the start of each run would remove the two inferences that remain.

Only then would it make sense to run more episodes per configuration and return to the questions the four-condition ladder was meant to answer: how far performance falls from training seeds to new starting poses, to new layouts and to new task--item pairings.

\section{A staged route to physical validation}

Simulation results, even reproducible ones, are a filter rather than a destination. If a version-aligned baseline is established, a sensible route to physical validation would start with a single shelving unit matching the simulated dimensions, with calibrated cameras placed as in simulation, to separate visual domain shift from contact and controller effects. Real packaging, which is glossy, deformable or transparent in ways the rigid-body simulator does not capture, would come next. Only then would store-scale navigation and safety envelopes around people be worth adding, and reporting would shift from binary success towards measures a store operator cares about, such as items handled per hour, damage to neighbouring stock and the frequency of human intervention.

The step that comes before all of this is less glamorous. A released checkpoint needs a matching, versioned evaluation environment, and the version information has to be recorded at the time the results are produced. The two runs in this dissertation are an attempt to keep such a record.
